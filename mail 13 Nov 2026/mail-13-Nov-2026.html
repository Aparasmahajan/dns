Below is the current status of the DNS Management Portal, our plan for the coming weeks, and the inputs we need from Starlight and SBI to move to testing and a working prototype.

1. Current status

Development of the portal front end (React) and back end (Java / Spring Boot) is in progress. The local build already covers:

  • Sign-in with portal accounts and the Bank LDAP directory, access requests from new users, and the access levels Read, Read + Write, Checker, Admin and Auditor
  • Partitions and DNS records (one-to-one, one-to-many and PTR), with maker-checker approval and direct Checker/Admin changes
  • Scheduled changes, version history, version compare and rollback
  • An append-only audit trail and JSON log files ready to be forwarded to the SIEM

The F5 integration is built behind a single interface and currently runs against a simulated F5. We will connect it to a real device once the F5 API is confirmed and test access is available.

2. Plan for this week

  • Continue front-end and back-end development
  • Start unit and integration tests for the back-end API and the access rules
  • Prepare the F5 integration design: how a change is applied at DC, DR and AZ, and how a failure at one site is handled

5. What we need

From F5:

  • The BIG-IP DNS REST API documentation we requested earlier, and confirmation of whether the portal should call BIG-IP directly (iControl REST) or go through BIG-IQ. The F5 API links we are working from are listed in section 7 below. Please let us know if any change in the API approach is required.
  • How standard DNS records (A, AAAA, PTR) should be created and changed. F5 article K14724629 states that iControl REST does not support managing ZoneRunner (BIND). Please confirm F5's supported method for SBI's records, for example:
    • Wide IPs through the GTM API
    • DNS Express with zone transfers
    • DNS dynamic update with TSIG
  • A test F5 BIG-IP DNS (GTM), for example a BIG-IP VE, on the same software version as production, with a least-privilege API account and network access from our test server. This is required for F5 integration and integration testing (needed by 2-Dec-2026). We have a read-only check script ready to verify the API as soon as access is available.

From SBI:

  • A test server for deploying the portal on RHEL 9 (sizing below). It needs network access to the test F5 management interface, the Bank LDAP directory over LDAPS, and a test SIEM endpoint.
  • SBI's requirements for the working prototype:
    • the scope and use cases to demonstrate
    • test users for each access level
    • sample DNS data
    • the site (DC or DR) and the date
    • the acceptance criteria

Test environment sizing (Solution Proposal v2.1 section 6.4; Requirements Specification v1.0 section 14.1):

  • Portal App/API: 1–2 nodes, 8–16 vCPU, 16 GB RAM, 120–180 GB storage
  • PostgreSQL: 1–2 nodes, 8–16 vCPU, 16–32 GB RAM, 300–500 GB storage
  • Log forwarder: 1 node, 2–4 vCPU, 4–8 GB RAM, 50–100 GB storage
  • Utility / bastion: 0–1 node, 4–8 vCPU, 8–16 GB RAM, 60–80 GB storage (the Bank bastion can be reused where available)

The second application and database nodes are needed only if SBI wants a high-availability / failover rehearsal in UAT.
